# План рефакторинга Telegram-бота

## Масштаб проекта

Бот решает одну задачу: по расписанию создаёт опрос, считает голоса и помогает
учитывать приглашённых игроков через `+1`. Архитектура должна оставаться
небольшой и понятной одному разработчику.

Цель рефакторинга — надёжно сохранить состояние и корректно обрабатывать
голоса, перезапуски и ошибки Telegram. Отдельная платформа релизов, сложная
инфраструктура и внешний сервис мониторинга этому проекту не нужны.

## Приоритет 1 — надёжность основных сценариев

Статус: выполнено локально.

1. **Подсчёт голосов**
   - учитывать ответы самого Telegram-опроса;
   - принимать только точные команды `+1` и `+1 ФИО`;
   - показывать безымянного гостя как «Гость от Имя»;
   - сохранять указанное ФИО;
   - корректно удалять ручной голос по `-1`.

2. **Изменение критического количества участников**
   - сообщать, когда после отказа участников становится меньше установленного
     порога;
   - отдельно сообщать об уходе при запасе участников, например с 12 до 11;
   - не отправлять повторные сообщения без фактического изменения результата.

3. **Состояние**
   - записывать `state.json` атомарно;
   - перед заменой сохранять `state.json.bak`;
   - восстанавливаться из резервной копии при повреждении основного файла;
   - поддерживать чтение состояния старого формата.

4. **Расписание и перезапуск**
   - восстанавливать активные задания после старта;
   - корректно обрабатывать пропущенное задание;
   - исключать повторное создание одного опроса;
   - безопасно переживать удалённый или уже закрытый опрос.

5. **Ошибки Telegram**
   - закреплять сообщение только после успешной отправки;
   - не считать временную ошибку Telegram успешной операцией;
   - не падать целиком из-за ошибки в одном обработчике.

## Приоритет 2 — понятный код

Статус: выполнено локально.

Код разделён по реальным обязанностям:

- `main.py` — точка запуска;
- `bot.py` — сборка приложения и административные команды;
- `handlers/polls.py` — создание и завершение опросов;
- `handlers/votes.py` — команды `+1`, `-1` и статус;
- `votes.py` — правила подсчёта и тексты;
- `storage.py` — состояние бота;
- `scheduling.py` и `schedule_commands.py` — расписание;
- `announcements.py` — временные объявления;
- `config.py` — настройки;
- `health.py` — простой heartbeat;
- `models.py` — структуры сохранённых данных.

Модули не следует дополнительно дробить, пока в них не появятся разные
независимые обязанности. Общие интерфейсы, контейнеры зависимостей и отдельные
слои репозиториев для текущего размера бота не вводятся.

## Приоритет 3 — проверки и эксплуатация

Статус: выполнено локально.

1. Автоматические тесты проверяют подсчёт голосов, хранение состояния,
   расписание и основные обработчики.
2. Ruff проверяет форматирование и явные ошибки.
3. CI запускает проверки при изменениях.
4. Production использует один каталог `/opt/bot_tg` и один systemd-сервис.
5. Деплой копирует актуальные файлы, ставит зависимости, перезапускает сервис
   и ждёт свежий heartbeat.
6. Для изменений поведения Telegram при наличии тестового токена можно
   запустить stage-бота вручную.

## Что сознательно исключено

Для текущего бота не внедряем:

- каталоги версий, симлинк `current` и хранение нескольких релизов;
- автоматический rollback;
- отдельный GitHub Environment и обязательный ruleset;
- обязательный stage-деплой для каждой правки;
- отдельный проект мониторинга;
- собственную систему алертов и метрик;
- новые архитектурные слои без новой бизнес-логики.

Если бот получит несколько независимых функций, несколько экземпляров или
базу данных, необходимость этих решений можно оценить заново.

## Осталось перед публикацией

1. Проверить локальный diff и результаты тестов.
2. При изменении пользовательского сценария проверить stage-бота, если
   доступны его токен и чат.
3. Отправить ветку в Git только по явной команде.
4. После попадания изменений в `main` убедиться, что GitHub Actions завершился
   успешно, systemd-сервис активен, а heartbeat свежий.

## Критерий завершения

Рефакторинг завершён, когда:

- команды и подсчёт голосов работают по описанным правилам;
- состояние не теряется при обычном перезапуске и восстанавливается из
  резервной копии;
- расписание восстанавливается после старта;
- тесты и Ruff проходят;
- запуск и деплой описаны в `README.md` и `OPERATIONS.md`;
- структура проекта остаётся соразмерной одной задаче бота.
