# План рефакторинга Telegram-бота

## 1. Цель

Привести бота к состоянию, в котором изменения логики голосования, расписания и уведомлений можно выпускать без риска потерять состояние опроса или случайно нарушить работу рабочего чата.

Рефакторинг выполняется постепенно. Каждый этап должен сохранять рабочее поведение бота, проходить автоматические проверки в отдельной ветке и только после проверки попадать в `main`.

## 2. Текущее состояние

- Основная логика всё ещё сосредоточена в `bot.py`, хотя конфигурация, хранение,
  объявления, расписание, сообщения и часть бизнес-правил уже вынесены в модули.
- Конфигурация, состояние, Telegram-обработчики, расписание и бизнес-правила используют общие глобальные переменные.
- Состояние хранится в одном `state.json` и записывается непосредственно в целевой файл.
- Добавлен локальный набор автоматических тестов; изменения ещё не опубликованы.
- Подготовлены обязательные lint, format и pytest-проверки перед production-деплоем.
- Ветка `main` не защищена и непосредственно связана с production-деплоем.
- Production-сервис работает от `root` без systemd hardening.
- Репозиторий публичный; Dependabot, secret scanning и code scanning отключены.

## 5. P0 — обязательные исправления до рефакторинга структуры

### P0.1. Зафиксировать критическое поведение тестами

**Проблема:** сейчас любое изменение проверяется только через `py_compile`. Ошибка в подсчёте голосов или переключении порога попадёт в production.

**Действия:**

1. Добавить `pytest` как dev-зависимость.
2. Создать фабрики тестового состояния опроса и фальшивого Telegram-бота, который сохраняет отправленные сообщения.
3. Покрыть переходы количества голосов:
   - `8 → 9`;
   - `9 → 10`;
   - `12 → 11`;
   - `11 → 10`;
   - `10 → 9`;
   - `9 → 8`;
   - повторный набор `9 → 10`.
4. Покрыть реальные и виртуальные голоса отдельно.
5. Проверить `+1`, `+1 ФИО`, `/plus1`, `/minus1`, обычный `-1` и `/status`.
6. Проверить повторный запуск бота с сохранённым состоянием.

**Критерии готовности:**

- Тесты не обращаются к настоящему Telegram API.
- Все перечисленные переходы проверяют счётчик, флаги и точный тип уведомления.
- Тесты запускаются одной командой `pytest`.
- CI не допускает деплой при падении тестов.

### P0.2. Не снимать чужие закреплённые сообщения

**Проблема:** при создании опроса бот вызывает `unpin_all_chat_messages` и снимает все закрепы группы.

**Действия:**

1. Хранить `message_id` предыдущего опроса.
2. Перед закреплением нового опроса снимать только предыдущий опрос через `unpin_chat_message`.
3. Если старого `message_id` нет, не выполнять массовую очистку.
4. Ошибку снятия старого закрепа логировать, но не блокировать создание нового опроса.
5. Добавить тест, доказывающий отсутствие вызова `unpin_all_chat_messages`.

**Критерии готовности:**

- Посторонние закрепы в группе сохраняются.
- Новый опрос закрепляется.
- Отсутствующий или уже снятый старый закреп не ломает запуск опроса.

### P0.3. Ограничить контекст команды `/announce`

**Проблема:** ожидание объявления хранится только по ID администратора. Следующее текстовое сообщение этого администратора из другого чата может быть опубликовано в рабочую группу.

**Действия:**

1. Хранить контекст как минимум по `(admin_id, source_chat_id)`.
2. Принимать текст объявления только в том чате, где была вызвана `/announce`.
3. Использовать `ConversationHandler` или собственное состояние с временем истечения.
4. Добавить таймаут ожидания, например 5 минут.
5. После таймаута, `/cancel`, успешной отправки или ошибки очищать состояние.
6. Перед публикацией показывать администратору предпросмотр с кнопками «Опубликовать» и «Отмена».
7. Проверять ограничение Telegram на длину сообщения до отправки.

**Критерии готовности:**

- Сообщение из другого личного или группового чата никогда не публикуется.
- Объявление нельзя отправить после таймаута.
- Публикация происходит только после явного нажатия «Опубликовать».
- Есть тесты для правильного чата, чужого чата, отмены и таймаута.

### P0.4. Сделать запись состояния атомарной

**Проблема:** сбой процесса или диска во время `json.dump` может оставить повреждённый `state.json`. После этого бот стартует с пустым состоянием и может создать повторный опрос.

**Действия:**

1. Вынести хранение состояния в отдельный `StateRepository`.
2. Записывать JSON во временный файл в той же директории.
3. Выполнять `flush` и `os.fsync` перед заменой файла.
4. Заменять основной файл атомарно через `os.replace`.
5. Хранить последнюю корректную копию `state.json.bak`.
6. Добавить поле `schema_version`.
7. При ошибке чтения пробовать резервную копию.
8. Если обе копии повреждены, завершать запуск с явной ошибкой, а не молча продолжать с пустым состоянием.

**Критерии готовности:**

- Прерывание записи не повреждает последнюю корректную версию.
- Восстановление из `.bak` проверено тестом.
- Ошибка состояния видна в systemd и мониторинге.
- Production-деплой не удаляет файлы состояния.

### P0.5. Устранить гонку между `PollAnswer` и `Poll`

**Проблема:** Telegram присылает имя проголосовавшего и агрегированный счёт разными обновлениями. При неблагоприятном порядке бот может очистить список имён или связать уход с неправильным человеком.

**Действия:**

1. Не очищать весь `yes_voters`, если агрегированный счёт временно меньше количества известных имён.
2. Хранить последнее состояние выбора каждого пользователя отдельно от агрегированного счётчика.
3. Добавить очередь ожидающих изменений либо короткое согласование событий по `poll_id`.
4. Для уведомления об уходе использовать конкретное изменение пользователя, когда оно доступно.
5. Если имя определить невозможно, отправлять нейтральное сообщение только после согласования счётчика.
6. Проверить оба порядка событий: `PollAnswer → Poll` и `Poll → PollAnswer`.
7. Проверить быстрые последовательные изменения нескольких пользователей.

**Критерии готовности:**

- Оба порядка Telegram-обновлений приводят к одинаковому состоянию.
- Известные имена не очищаются из-за временного расхождения счётчиков.
- Уведомление об уходе не использует имя предыдущего пользователя.
- Итоговый счёт всегда берётся из агрегированного Telegram poll update.

## 6. P1 — надёжность работы и production

### P1.1. Восстанавливать пропущенные задачи расписания

**Проблема:** расписание создаётся в памяти при запуске. Если бот был выключен в момент задания, новый планировщик не восстановит уже прошедший запуск только благодаря `misfire_grace_time`.

**Действия:**

1. При старте выполнять процедуру `reconcile_schedule`.
2. Определять, должен ли сегодня существовать активный опрос.
3. Если время опроса прошло, но время закрытия ещё не наступило и опрос не создан, создать его один раз.
4. Аналогично проверить дедлайн и напоминание.
5. Не отправлять просроченное напоминание после времени закрытия.
6. Хранить отметки выполненных задач по дате.
7. Проверить рестарты до опроса, после опроса, после дедлайна, перед напоминанием и после закрытия.

**Критерии готовности:**

- Перезапуск в допустимом временном окне восстанавливает пропущенную задачу один раз.
- Повторные рестарты не создают дубликаты.
- Старые задачи предыдущего игрового дня не выполняются.

### P1.2. Исправить сохранение флагов и переходов состояния

**Действия:**

1. Сохранять `notified_deadline` сразу после изменения.
2. Удалить двойной вызов `save_state` при обработке положительного голоса.
3. Удалить неиспользуемый `state_changed` либо использовать единый механизм dirty-state.
4. Описать переходы опроса: `created`, `quorum_reached`, `quorum_lost`, `closed`.
5. Запретить уведомления закрытого опроса.
6. При ошибке `stop_poll` не удалять состояние без отметки о необходимости повторной попытки.

**Критерии готовности:**

- Каждый переход состояния сохраняется один раз.
- После рестарта уведомления не дублируются.
- Неудачное закрытие можно повторить безопасно.

### P1.3. Сделать виртуальные голоса структурированными

**Проблема:** сейчас виртуальный голос хранит только подпись. Нельзя определить автора, удалить конкретного гостя или надёжно провести аудит изменений.

**Действия:**

1. Хранить для каждого виртуального голоса:
   - уникальный ID;
   - отображаемое ФИО;
   - ID и имя добавившего пользователя;
   - дату и время добавления;
   - источник: `plain +1` или `/plus1`.
2. Сохранить совместимость со старым форматом через миграцию состояния.
3. Добавить удаление конкретного гостя, а не только последнего глобального голоса.
4. Определить правило повторного добавления одинакового ФИО.
5. Ограничить длину и нормализовать пробелы в ФИО.

**Критерии готовности:**

- Старый `state.json` загружается без потери голосов.
- `/status` показывает понятные подписи.
- Администратор может удалить выбранного гостя.
- В логах видно, кто добавил или удалил виртуальный голос.

### P1.4. Перевести systemd-сервис с `root`

**Действия:**

1. Создать системного пользователя и группу `tg-poll-bot` без shell-доступа.
2. Передать ему `/opt/bot_tg`, `.env`, `state.json` и журналы.
3. Оставить `.env` и `state.json` с правами `600`.
4. Добавить в unit-файл:
   - `User=tg-poll-bot`;
   - `Group=tg-poll-bot`;
   - `NoNewPrivileges=true`;
   - `PrivateTmp=true`;
   - `ProtectSystem=strict`;
   - `ProtectHome=true`;

   - ограниченный `UMask`;
   - минимальный набор допустимых системных вызовов после проверки совместимости.
5. Проверить исходящие HTTPS-запросы Telegram и запись состояния.
6. Повторно выполнить `systemd-analyze security`.

**Критерии готовности:**

- Бот работает без root-прав.
- Планировщик, логи и состояние продолжают работать.
- После рестарта сервера сервис запускается автоматически.
- Оценка systemd exposure существенно ниже текущих `9.6 UNSAFE`.

### P1.5. Сделать деплой атомарным и добавить откат

**Проблема:** workflow перезаписывает рабочие файлы, обновляет окружение на месте и только затем перезапускает сервис.

**Действия:**

1. Собирать архив релиза в GitHub Actions.
2. Загружать его в `/opt/bot_tg/releases/<commit_sha>`.
3. Создавать отдельное виртуальное окружение релиза или проверять зависимости до переключения.
4. Выполнять синтаксические тесты и импорт приложения внутри нового релиза.
5. Переключать симлинк `/opt/bot_tg/current` только после успешных проверок.
6. Перезапускать systemd и выполнять smoke-check.
7. При неуспешном старте возвращать предыдущий симлинк и снова запускать сервис.
8. Хранить последние 3–5 релизов.
9. Не отменять workflow посередине выкладки; пересмотреть `cancel-in-progress: true`.

**Критерии готовности:**

- Неудачная версия не заменяет работающую.
- Откат выполняется автоматически.
- `state.json`, `.env` и логи находятся вне каталога конкретного релиза.
- В GitHub Actions виден результат smoke-check и версия production.

### P1.6. Добавить прикладной health-check

**Действия:**

1. Проверять не только `systemctl is-active`, но и время последнего успешного Telegram polling/update.
2. Добавить команду или локальный health-файл с:
   - временем запуска;
   - временем последнего успешного обращения к Telegram;
   - статусом планировщика;
   - датой активного опроса;
   - ошибкой чтения или записи состояния.
3. Подключить проверку к существующему `uptime-monitor.timer`.
4. Уведомлять администратора только после нескольких последовательных ошибок.

**Критерии готовности:**

- Мониторинг выявляет зависший polling при активном systemd-процессе.
- Кратковременная сетевая ошибка не создаёт лишний шум.
- После восстановления отправляется отдельное уведомление.

## 7. P2 — разделение `bot.py` на модули

### P2.1. Вынести конфигурацию

Создать `config.py` и типизированный `Settings`.

**Действия:**

1. Загружать `.env` только в точке входа.
2. Проверять обязательные переменные и выводить понятную ошибку.
3. Валидировать `CHAT_ID`, список администраторов, порог, timezone и логирование.
4. Удалять дубликаты из `ADMIN_IDS`.
5. Не читать переменные окружения на уровне импорта бизнес-модулей.

### P2.2. Вынести модели состояния

Создать `models.py` с `dataclass`, `TypedDict` или обычными классами для:

- `PollState`;
- `ManualVote`;
- `ScheduleConfig`;
- `PendingAnnouncement`;
- отметок выполнения задач.

Каждая модель должна иметь явное преобразование в JSON и миграцию предыдущего формата.

### P2.3. Вынести хранилище

Создать `storage.py`:

- загрузка и атомарное сохранение;
- резервная копия;
- версия схемы;
- миграции;
- единая обработка ошибок;
- отсутствие зависимости от Telegram API.

### P2.4. Вынести бизнес-логику голосования

Создать `poll_service.py`:

- создание и закрытие состояния опроса;
- реальные и виртуальные голоса;
- вычисление итогового количества;
- переходы через порог;
- формирование событий `AlmostReached`, `QuorumReached`, `VoteRemoved`, `QuorumLost`;
- отсутствие прямой отправки Telegram-сообщений.

Обработчик Telegram должен передавать входные данные сервису и отправлять полученные события.

### P2.5. Вынести уведомления и тексты

Создать `notifications.py` или `messages.py`:

- все тексты сообщений в одном месте;
- форматирование HTML/Markdown;
- единый стиль сообщений;
- функции для безопасного экранирования пользовательских ФИО;
- разделение сообщений рабочего чата и личных сообщений администраторов.

### P2.6. Разделить Telegram-обработчики

Создать каталог `handlers/`:

- `polls.py` — Telegram poll updates;
- `votes.py` — `+1`, `/plus1`, `/minus1`, `/status`;
- `admin.py` — `/announce`, `/settime`, `/setdays`;
- `common.py` — `/start`, неизвестные команды и сообщения об ошибках.

Права администратора проверять единым декоратором или фильтром.

### P2.7. Вынести планировщик

Создать `scheduler.py`:

- регистрация задач;
- изменение расписания;
- восстановление пропущенных событий;
- контроль уникальности job ID;
- корректное завершение при остановке приложения.

### P2.8. Оставить минимальную точку входа

После разделения `main.py` должен только:

1. загрузить настройки;
2. настроить логирование;
3. создать хранилище и сервисы;
4. собрать Telegram Application;
5. зарегистрировать обработчики;
6. запустить polling.

**Общие критерии готовности P2:**

- Нет глобального изменяемого состояния в бизнес-модулях.
- Бизнес-правила тестируются без Telegram.
- Каждый промежуточный коммит сохраняет работоспособность.
- Поведение сообщений не меняется без отдельного согласованного требования.
- Покрытие критической бизнес-логики тестами составляет не менее 80%.

## 13. Итоговые критерии завершения рефакторинга

Рефакторинг считается завершённым, когда:

- критическая логика голосования покрыта автоматическими тестами;
- CI обязателен перед production-деплоем;
- бот не снимает чужие закрепы;
- `/announce` нельзя случайно активировать сообщением из другого чата;
- состояние записывается атомарно и восстанавливается из резервной копии;
- оба порядка Telegram poll updates дают одинаковый результат;
- пропущенные задания расписания корректно восстанавливаются;
- production-сервис работает без root-прав;
- деплой имеет автоматический откат;
- мониторинг проверяет реальную работоспособность polling;
- код разделён на конфигурацию, модели, хранилище, сервисы, обработчики и планировщик;
- `main` защищён, security-функции GitHub включены;
- stage-запуск и эксплуатационные инструкции соответствуют реальному проекту;
- после всех изменений проведён полный stage-тест и контролируемый production-релиз.
